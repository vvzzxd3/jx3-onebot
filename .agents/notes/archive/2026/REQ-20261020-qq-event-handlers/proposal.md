# QQ 事件封装与业务装饰器：详细评审提案

> 类别：proposal；所属需求：[REQ-20261020-qq-event-handlers](<index.md>)；日期：2026-10-20；状态：**维护者已批准实施，离线实现及验收见 [需求索引](<index.md>)**。下文保留评审时原文，其“拟议”“待实施”等表述只代表当时状态；现行接口以[业务路由代码](<../../../../../src/jx3_bot/routing.py>)、[开发指导](<../../../../../AGENTS.md>)为准。

## 一、目标与设计原则

借鉴 NoneBot 的功能形式：用装饰器声明消息类型、内容匹配条件和执行顺序；匹配成功后调用异步处理函数，按其声明提供事件数据、匹配参数和已登记的业务服务。同一函数可声明群聊和私聊等多个入口。业务函数不接触 WebSocket 帧、SQLite、水位或 QQ HTTP；实现不依赖 NoneBot 本体、适配器、异常式发送控制或跨平台兼容层。命令前缀由本应用配置，默认留空而非默认 `/`。

已由维护者明确：`GROUP_AT_MESSAGE_CREATE` 即群 @ 机器人事件，`content` 已去掉 @ 机器人前缀；单聊不存在 `AT_ME`；业务方应能直接写 `@on_group`／`@on_private`，内部的 `scene` 不暴露为业务配置。保留现有 5 分钟被动回复／预算／聊天归档、先持久化后匹配、固定一次 outbox 发送及失败不跳可靠序号的边界。

## 二、拟议业务 API（先评审，再确定）

### 2.1 业务处理函数形态

```python
from jx3_bot.routing import on_group, on_private
from jx3_bot.core.models import Reply
from jx3_bot.integrations.qq.models import GroupMessageEvent, PrivateMessageEvent

@on_group(match="天气", at_me=True, priority=10, block=True)
@on_private(match="天气")
async def weather(event: GroupMessageEvent | PrivateMessageEvent, args: str) -> Reply | None:
    # 「天气 北京」的 args 为「北京」；「天气」的 args 为 ""，业务后续可使用默认参数。
    ...

@on_group()  # 默认 at_me=False；未指定 match 时匹配普通群事件的受支持文本
async def ordinary_group_text(event: GroupMessageEvent) -> Reply | None:
    ...
```

- 业务装饰器**不要求 `name`**。当前代码会将尚未执行的业务任务保存在 inbox，重启后按 matcher 名称继续调用业务函数（见[现有分发](<../../../../../src/jx3_bot/matching.py#L103-L118>)）；维护者现已明确**因重启而未触发的业务直接忽略，不需要补执行**。对重启前已开始但未规划回复的函数也不应未经确认就重新调用，以免重复业务副作用；该边界待实施时明确。拟议实现只需在当前进程内区分不同装饰器／函数，注册时检测重复与歧义，不为了跨进程找回处理函数强制业务填写稳定 ID 或维护改名映射。此变更尚未实施，不能把当前代码的恢复行为冒称已撤销。
- `match` 合并原 `command` 与 `fullmatch` 的业务用法：从正文首字开始识别**完整关键字**，后面只能是正文结束，或至少一个空白字符再接**非空参数**。例如 `match="天气"` 匹配 `天气`（传入 `args=""`）和 `天气 北京`（传入 `args="北京"`），不匹配 `天气预报`、`天气北京`；是否使用默认值由后续业务处理，装饰器不擅自增加默认参数机制。参数首尾空白按现有匹配方式去除，仅有尾随空白时视为无参数形式；文字严格区分大小写。允许在应用配置文件中配置 `command_prefix`，默认留空；配置 `/` 后只匹配 `/天气` 或 `/天气 北京`，不匹配无前缀形式，前缀不作为 `args` 的一部分。群 @ 事件的正文已去掉 @ 机器人前缀；普通群正文若以提及文本开头，不擅自剥离。不指定 `match` 时才显式匹配该场景已支持的**文本消息**，并防止原 `invalid` 命令被当作正常全文交给业务；正则等其他内容匹配形式留待另行评审，不捏造本轮 API。
- `at_me: bool = False`：`on_group` 省略时只匹配 `GROUP_MESSAGE_CREATE`；显式 `True` 只匹配 `GROUP_AT_MESSAGE_CREATE`。不接受 `None` 或其他类型；`on_private` 不接受 `at_me` 参数，私聊事件类型模型也**不提供** `at_me` 属性。
- 一个函数可以叠加多个 `@on_group`／`@on_private` 装饰器，分别注册规则；同一入站消息首次命中该函数并调用一次后，停止检查**该函数余下的装饰器**，但不跳过其他函数，其他函数仍按 `priority`／`block` 规则处理。叠加规则的确定性顺序在编译时固定，不能依赖文件系统遍历顺序。`priority` 越小越先执行，默认 10；`block=True` 阻断**更低优先级**，不屏蔽同优先级已匹配处理器。多处理器输出仍聚合为**同一条**被动回复并受 1800 字及安全校验限制，不因多个函数而重复 POST；返回 `None` 即不回复。
- 处理函数只接受有限参数：对应事件类型的 `event` 与 `match` 提取出的 `args: str` 可按需声明；无 `match` 时不提供 `args`，不把全文混作参数；无业务依赖时也可使用零参数函数。同一函数叠加群聊／私聊装饰器时可声明两者的联合事件类型。业务服务注入见 §2.3；启动时验证函数为 `async def`、形参／注解与路由类型兼容，返回值在运行时验证为 `Reply | str | None`；错误签名应拒绝启动，错误业务返回值不被默默转成任意对象字符串。
- `on_group` 只根据收到的群消息**事件类型 `t`** 与 `at_me` 的布尔值决定是否匹配，不扫描 `content` 中的 `@`，也不根据尚未验证的两类事件推送关系改变判断。

### 2.2 事件类型与数据安全

建议引入冻结的、只读的 `GroupMessageEvent` 与 `PrivateMessageEvent`，两者共有受限属性：`app_id`、`message_id`（QQ `d.id`）、`user_id`、`content`、`timestamp`、`event_type`、`sender_name` 及对应会话标识；群类型额外有 `group_id`、`at_me: bool`，私聊有 `user_openid`，**没有** `at_me`。`content` 是有授权的业务处理所需的入站正文（沿用现有入库前凭据脱敏／截断，不等于可公开日志）；匹配仍受 4096 字上限，非文本／截断文本暂不进入通用文本装饰器，但继续按现有策略归档和输出允许的日志。没有 `raw_payload`、token、`message_scene.ext`、附件 URL、QQ HTTP 客户端或底层 Store 引用。

`AT_ME` 是业务语义而不是新造的官方 `t` 枚举；群 `GROUP_AT_MESSAGE_CREATE` → `at_me=True`，普通群 `GROUP_MESSAGE_CREATE` → `False`；`C2C_MESSAGE_CREATE` → `PrivateMessageEvent`，不计算 at_me。现有内部 `MatchContext.to_me` 曾把单聊也视为 true（参见[当前实现](<../../../../../src/jx3_bot/integrations/qq/events.py#L90-L108>)）；迁移时不可将该历史兼容值冒充私聊 `AT_ME`，旧 rule 接口维持兼容或增加单独适配再退出，不能直接改掉天气当前运行时行为；旧队列按 §2.2 的重启处置规则处理。

**重启后的业务处理边界已由维护者确认**：现行 `IncomingMessage` 会在 inbox 持久化，应用重启后恢复尚未完成的业务调用；拟议实现改为**不补执行重启前尚未触发的业务函数**，也不重新匹配其内容。启动时对上一进程遗留的未触发 inbox 业务任务以幂等方式标记为终结且无回复，使其不阻塞同会话后续任务；已开始但中断的任务不能未经评审就重新调用，以免重复产生业务副作用；具体状态和一次性恢复时序须先结合现有 FIFO／事务实现设计并用离线重启测试确认。不得因此删除已提交的聊天记录、重置数据库中保存的网关会话 ID 和接收序号，或擅自重发／删除已写入 outbox 的回复记录；记录仍在数据库中不代表可以直接重新发送，是否发送仍按现有状态、有效期限及重试限制处理。**未重启的正常消息**仍在原有持久化顺序后进行匹配、处理和回复；长期四表不新增 @ 标记，也不为跨重启重构完整事件而储存原始 QQ `d`。

### 2.3 注册、装配与业务服务注入

维护者要求**应用启动时自动发现并注册业务模块**，不要求新业务逐个修改入口来调用 `register_module`。建议只遍历本项目可信的 `jx3_bot.modules` 命名空间内符合约定的业务模块及其 `handlers`，按完整模块名排序后导入，收集模块内显式定义的带装饰器函数并编译为每个应用实例独立的 `MatcherRegistry`；不扫描站外文件系统、不导入任意第三方模块、不热加载。导入模块时装饰器只记录元数据，不能立刻修改全局注册表或触发网络／数据库操作；启动时统一验证重复发现、内部路由 ID 冲突、优先级、参数签名、不可满足的服务依赖，异常则明确拒绝启动。是否把未标注装饰器的 `handlers` 模块也视为正常空模块待实施评审，避免误报现有模块。

业务函数需要服务时，应用先按现有入口装配已知业务服务，再自动绑定到声明了受限注入标记的 handler，例如 `weather: WeatherService = Inject("weather")`。仅允许已登记的业务服务，启动时核对名称及类型；不凭注解扫描任意对象，不注入 QQ 客户端、Store、凭据或原始配置，不创建递归 DI 容器。新业务只需在约定目录定义装饰器函数，不需逐个手工注册或手工传入服务实例；迁移前已有 `weather_registry(weather.handle_result)` 保持可用。**装饰器、自动发现／注册与注入实施并验收后，应将实际目录约定、可用签名、配置、安全边界和迁移规则固化到 `AGENTS.md` 等现行开发指导文件，不能只留在本提案。**

### 2.4 当前匹配器与功能迁移

内部保留并演进现有[匹配器](<../../../../../src/jx3_bot/matching.py#L17-L118>)的 `MatcherRegistry`：装饰器是注册语法与群 @ 规则适配，旧 `on_command`／`on_fullmatch`／`on_regex`／`on_message` 可暂作内部设施／兼容接口。确保 `scene` 来自 QQ 解析结果，不要求业务提供。天气三个命令先以原[模块注册](<../../../../../src/jx3_bot/modules/weather/handlers.py#L5-L17>)为回归基线，后迁移至装饰器；无参数 `天气` 保持匹配并向业务传空 `args`。**旧 inbox 中尚未触发的业务任务在新启动时按上述规则终结而不重放**，不按旧 `kind` 或 matcher 名称路由到新处理器，也不因新 matcher 名称变化要求兼容映射；迁移切换不得删除已写入 outbox 的回复记录或聊天记录；前者仍按原有发送限制处理。

## 三、传输、解析、分发与发送边界

```text
QQ WS frame
  ├─ op=10/11/1/7/9 ... → 网关控制；心跳与 Resume、关闭码策略保持原实现
  └─ op=0 Dispatch → 校验 envelope(op,t,s,id,d)，按 t 映射事件解析器
        ├─ READY / RESUMED → 会话控制与数据库中保存的接收序号
        ├─ 支持的群/@/单聊 → 规范化为安全持久化消息投影
        └─ 未支持但含有效 seq 的 Dispatch → 安全类别/原因，无业务函数并提交水位；缺失/无效 seq 按现有策略报错停止，不跳水位
      → 有界接收队列 → 同一事务：聊天入站历史 + inbox 任务 + 网关会话 ID／接收序号
      → worker 认领已提交任务 → 单行聊天日志 → 类型+条件匹配 → 路由处理函数
      → 一个已验证的 Reply/文本结果 → 同一固定 seq 的 outbox
      → QQ HTTP 被动回复 → 确认成功后发送归档与成功日志
```

帧头 `id` 为**事件** ID，`s` 为 WS 网关序号，群／单聊消息 `d.id` 是去重和被动回复的**消息** ID；三者不能混用。[QQ payload 结构](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/event-emit/payload.html)、[WS Identify/Resume/Dispatch](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/event-emit/websocket.html)。`s` 的心跳最新接收值和事务提交的 Resume 水位继续分开；落库失败不跳号，新会话前按序排空已收队列。业务处理不运行在 socket 收包协程，不给业务传原始帧，不让 handler 直接发送 QQ 消息。应用入口控制显式装配、worker 并发、匹配、输出计划，业务只返回结果。

该次改动**只让已支持的消息事件可以被处理**。新增更多 QQ 事件时，为该类型先定义受限 DTO、是否需落盘／重放、唯一键与权限，再允许注册对应处理函数。未知事件按受限摘要观察并可靠确认，不能为了快速扩展把完整 `d` 自动存 inbox 或暴露给业务函数。现行请求/响应 DTO 完整校验不顺带大迁移。

## 四、现有处理边界与待验证事实

| 问题 | 当前行为／约束 | 建议的首版策略与边界 |
| --- | --- | --- |
| 相同群消息 `d.id` 是否会出现两类群事件 | 维护者提供的一次真实运行摘录中，同一 `trace` 只看到一条 `GROUP_MESSAGE_CREATE` 收帧和一次 `accepted`；这只能描述该样本，不能推断平台总是只发一种事件。现有 Store 以 `(app_id, scene, conversation_id, d.id)` 为稳定键去重；见[存储实现](<../../../../../src/jx3_bot/store.py#L201-L244>)。 | 不根据单个样本修改去重、路由或回复行为；`on_group(at_me=True/False)` 只按实际收到的事件类型匹配。已按维护者要求撤回本轮新增的专用诊断日志，提案不包含日志改造。 |
| Resume/重连重投与多事件 | 心跳最新接收 seq 不等于已持久化水位；消息稳定键用于业务去重。 | 保留当前消息与 checkpoint 同事务及 FIFO；事件 ID、seq 不能替代 d.id；未知事件需推进水位但不调用业务。 |
| 多个处理函数匹配、block 与出站 | 当前同优先级可多匹配，收敛到一个 outbox，POST 结果不确定不能自动重发。 | 保持最多一个消息回复计划／一次 HTTP 被动回复，组合回复超长触发原有安全处理；不得提供业务 handler 直接 `send()`。 |
| 重启前未触发的业务任务／旧 Command 结构 | 当前应用重启会恢复 inbox，旧 payload 可能存有 `matcher=""`。 | 新方案重启后终结旧 inbox 中未触发的业务任务，不补执行、不重新匹配也不生成回复；已开始但中断的任务不擅自重跑，实施时需明确安全的状态处置。已写入 outbox 的回复记录、聊天记录及保存的网关会话 ID／接收序号不因此删除或重置；复测重启与 FIFO，不重建数据。 |
| 错误／隐私 | handler 异常可能停止 worker；聊天正文默认归档，日志默认按维护者要求展示但脱敏。 | 启动期拒绝错误装饰器；运行时日志仅异常类型/route/trace，沿用现有 worker 故障保护与恢复；不允许任意原始事件流入持久化和日志，不借本需求改永久历史或控制台保留策略。 |

## 五、建议实施步骤、文件边界与验证门槛

1. **契约与测试先行**：固定 `match` 完整关键字后可结束或接空白＋非空 `args`、可配置／留空 `command_prefix`、群 `at_me=False` 默认值、无需业务 `name`、多个装饰器首次命中后只调用该函数一次及自动发现顺序；为[匹配测试](<../../../../../tests/test_matching_replies.py>)、[网关测试](<../../../../../tests/test_gateway.py>)和[聊天链路测试](<../../../../../tests/test_chat_pipeline.py>)增加合成事件、缺失依赖、重启和旧任务测试。分别检验两类群事件、私聊、配置前缀、参数词边界、失效 session 排空和落库回滚；不连接真实 QQ。
2. **QQ 接入分类**：在 `integrations/qq/` 引入 envelope 校验／固定事件枚举／群私聊安全 DTO，从[旧事件解析](<../../../../../src/jx3_bot/integrations/qq/events.py>)迁出可复用分类逻辑；[网关](<../../../../../src/jx3_bot/gateway.py>)仅处理传输控制及有界可靠接收，必要时保留旧导入兼容，不能改变 WS 直连与 Resume 行为。
3. **业务装饰器与启动自动发现**：在真正通用的行为模块中实现 `on_group/on_private` 元数据、`match` 参数解析、内部路由 ID 与启动期校验；应用在可信业务目录按确定性顺序自动发现并注册，基于已装配业务服务绑定受限依赖。[现有 MatcherRegistry](<../../../../../src/jx3_bot/matching.py>)仍负责条件匹配，应用在事务提交后派发。天气迁移时保留无参数 `天气` 的匹配并传入空 `args`，重启前遗留业务任务以幂等方式终结而非转移到新处理函数，验证已写入 outbox 的回复记录仍按原有状态、有效期限和重试限制处理；不为目录完整而创建空模块。
4. **实施后同步指导文件**：装饰器、启动自动发现／注册和受限注入验收后，将实际业务目录约定、配置示例、处理函数签名、重启旧任务处置与安全边界固化到[开发指导](<../../../../../AGENTS.md>)，按实际变化同步[README](<../../../../../README.md>)和[部署指南](<../../../../../docs/qq-integration/2026-10-10-deployment.md>)；本轮不修改这些正式文档，也不调整现有日志。
5. **离线回归与平台验收分开**：实施阶段执行 `uv run --locked python -m unittest discover -s tests -v`、`uv run --locked python -m compileall -q src/jx3_bot tests`（如涉及依赖再运行环境检查）。平台真实权限与 QQ HTTP 被动回复仅能由维护者授权的真实测试验证；不将离线模拟冒称平台验证。
