# QQ 官方机器人接入计划

- 建档：2026-10-10；最近更新：2026-10-13（Asia/Shanghai）
- 状态：历史迁移计划；组合方案已批准，独立WebSocket＋天气首版代码与离线验证完成，见 [当前实施](<2026-10-10-implementation.md>) 与 [已批准方案](<../weather/2026-10-10-confirmation-plan.md>)。下文旧Webhook建议／尚未实施描述按历史阅读；实际授权联调、旧依赖清理和正式切换未执行。
- 来源：维护者要求移除 NoneBot2、由个人号独立客户端转为 QQ 官方接入

- 官方资料：[QQ 机器人 API v2](https://bot.q.qq.com/wiki/develop/api-v2/)；初始建档仅记录入口，后续实际访问的鉴权、事件、签名与群消息资料见 [架构切换方案](<2026-10-10-architecture-migration.md>)（2026-10-10 核实，未做账号／群内实测）。

## 当前事实与目标

当前入口（历史路径 `bot.py`，已清理） 初始化 NoneBot2 并注册 OneBot V11，现有插件（历史路径 `src/plugins/`，已清理） 依赖 NoneBot 事件处理接口，其中部分直接引用 OneBot 消息类型。

目标是由 Python 服务端直接对接 QQ 官方机器人，实现事件接收、业务处理和官方消息回复，不再依赖个人号客户端、NoneBot2 或 OneBot 适配层。仅支持 QQ，无多平台规划，新方案暂不支持 OneBot 标准。

非目标：开发新的个人号 QQ 客户端、通用多平台适配框架、OneBot 兼容层，或在没有能力核实的情况下承诺全量群消息采集。

## 方案摘要与关键依据

先以官方接口能力验证最小闭环，再按实际需求迁移业务逻辑。旧插件存在框架及消息类型耦合，不能简单删除依赖后原样加载。业务处理与 QQ 接入可保持清晰边界，但不因此引入暂无需求的通用协议抽象。

初始建档时，服务端框架、事件接收方式、持久化方案和部署拓扑均未选定。2026-10-10 维护者后续确认优先独立 WebSocket 接入层、群主开启全量消息、首个功能为天气，最新模块设计见 [WebSocket 方案](<2026-10-10-websocket-plan.md>)，跨模块前置确认见 [需求记录](<../project/2026-10-10-websocket-weather.md>)。具体存储与运行细节仍待实现；本记录不是已完成的接入。

## 执行步骤

1. **核实官方能力与准入**
   - 确认应用类型、账号／审核状态、目标群权限、开发与生产环境要求。
   - 查验当时官方支持的事件接收方式、鉴权和消息发送流程、限流及回复条件，记录具体资料链接与核实日期。
2. **确定最小设计并记录决策**
   - 根据实际官方支持选择事件接收方式和 Python 服务端实现。
   - 明确凭证管理、事件真实性校验（按选定方式适用）、访问控制、错误处理与运行配置。
   - 为官方事件重投、重复消息、超时、限流和凭证刷新设计处理规则，不在未核实前填写具体接口参数。
3. **实现官方接入最小闭环**
   - 在获得授权的测试场景中验证事件接收、简单指令处理、官方 API 回复。
   - 使用脱敏样本补充本地测试，失败路径覆盖鉴权错误、重复事件、发送失败和网络异常。
4. **迁移已确认需要的业务能力**
   - 建立旧功能与新处理逻辑的对应关系；去除对 NoneBot 和 OneBot 类型的业务耦合。
   - 优先实现维护者已确认需要的剑网 3 查询能力，不默认迁移全部实验插件。
5. **切换与清理**
   - 群内试运行并记录结果，更新启动方式、配置说明及运维方案。
   - 在新入口验证完成后移除旧入口及不再需要的依赖，停止依赖个人号独立客户端。
   - 确认部署不再需要 NoneBot2 和 OneBot；保留迁移记录而非强制保留旧协议兼容。

## 验收建议

- 使用 QQ 官方机器人身份完成已授权场景中的事件处理及回复，部署不依赖个人号客户端。
- 运行依赖、入口和业务代码不再依赖 NoneBot2／OneBot；文档准确反映新部署方式。
- 已验证权限、凭证失效、事件重投、超时和限流等关键异常，记录真实结果。
- 不将凭证或原始敏感消息写入日志，具备必要告警、操作记录与故障处置方案。

## 风险与待确认项

官方应用权限、事件范围、部署环境、测试群、框架选型及运维要求待确认。特别是“机器人可以入群”不代表“可以读取所有群消息”。
