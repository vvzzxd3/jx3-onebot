## 1. 当前事实、目标与非目标

旧天气代码存在 Redis 配置字段、处理器绑定与查询函数缺口，不能视为已可用。现有模型针对实时天气，不覆盖本次每日预报接口。当前没有城市偏好、天气缓存或统一调用预算数据库。

目标：通过官方 QQ 群命令处理用户主动城市输入、消歧并查询每日预报，节约请求、明确天气来源和数据时效；将预算管控集中在和风客户端，不把它散落在命令处理器。

非目标：下载全量城市／构建 GeoAPI 索引、默认收集群消息或定位、静默保存接口数据、使用真实凭证和付费 API 进行验证，修复旧天气插件全部缺陷或自动迁移旧密钥。

## 2. 实际核实的接口（2026-10-10）

| 项目 | 当前官方文档 | 实现方向 |
| --- | --- | --- |
| API Host | 使用帐号独立的 API Host | 配置 `https://<独立主机>`，不沿用旧公共 geoapi／devapi 主机 |
| 城市搜索 | `GET /geo/v2/city/lookup`，location 必填，adm／range／number／lang 可选 | 用户输入触发，明确同名地区；name／id／adm1／adm2／lat／lon／tz 等字段用于当前处理流程 |
| 每日预报 | 用户指定页面现为 `GET /weather/v1/daily/{latitude}/{longitude}`；坐标最多两位小数，days=1–10，默认7 | 建议首版3天，使用搜索获知的坐标；不把该接口写成 location=城市ID |
| 时间与返回 | v1 默认UTC，localTime=true 可返回地点本地时间；返回 metadata、days、daytime、nighttime、temperatureMax／Min | 使用新结构，按地点时区正确解释日期；不直接沿用旧 code/daily/tempMax 解析器 |
| 鉴权 | JWT（Bearer）或 API Key Header 二选一，官方推荐JWT | 与 QQ Token 分开管理；JWT需开发者／项目／凭据ID与安全注入的 Ed25519 密钥，不打印令牌 |
| 来源 | metadata.attributions 必须与数据共同显示 | 返回天气时保留来源声明；QQ URL／内容限制需上线前测试，不能默默删除必需归因 |

## 3. 已确认：自然月不超过50,000次免费份额

官方天气与基础服务（含GeoAPI）每自然月合计首50,000次免费。维护者明确更正最初口误，当前需求只以月免费份额为主保障，不启用“每日50,000、允许月超额付费”模式。此前讨论的日限候选属于确认过程，不是当前方案。

建议所有和风请求（Geo、天气、失败、重试）发出前通过同一持久化原子月预算；耗尽后停止外部请求，仅返回仍有效的天气缓存或清晰提示，不能依靠免费余额用完让供应商自动停止后付费。

### 计数与保障边界

- 为保守不超额，每次外发尝试占位，失败／超时／重试不回退，缓存命中不计调用。官方非2xx不计供应商请求次数，本地预算不等于准确账单。
- 月计数事务在网络请求前提交，存储异常拒绝请求，重启不清零、并发不超卖；凭据轮换不获得新免费份额。
- 帐号价格分组共享额度，不能每个用户／群／endpoint／项目各设50,000；需要扣除同帐号初始已用量和其他客户端消耗，单一本地数据库不保证整个帐号免费。
- 多进程使用同一SQLite须事务，多主机之前需共享存储或集中请求入口，不能各自从零计数。
- 账单月重置时区未核实，统计API的UTC不能推出账单边界；向供应商确认，期间采取更保守跨月预算而非盲目清零。
- 同一周期不能删除重建预算库或恢复旧快照；需备份／操作规程与初始已用量导入。

## 4. 城市来源：前置评估已完成，最终选择待确认

用户选择“先评估可授权本地城市库”，不是批准保存GeoAPI返回数据。完整许可证据、固定版本与内存解析见 [城市源评估](<2026-10-10-city-source-evaluation.md>)。

- 和风官方可下载列表：本次实际解析3,577条记录，有中文名、行政区、时区、经纬度；技术匹配度高，但未找到独立开放许可。本地索引／修改／随程序分发范围须明确，不把公开列表等同GeoAPI回包，也不直接断言官方列表全面禁止下载使用。
- GeoNames：官方导出明确CC BY 4.0，作为可落库的开放来源候选；中文别名、区县覆盖与坐标质量尚未做数据样本验收。推荐进入小样本验证，最终来源未批准。
- GeoAPI：继续可用于实时城市搜索，不默认落库城市ID／名称／坐标。FAQ／使用限制的缓存措辞宽窄不同，未找到保存少量结果的明确豁免。
- 用户自有输入与偏好可单独管理，普通聊天／其他用户位置不采集；偏好作用域、保留期与删除机制在实施前明确。
- 同名城市展示行政区消歧，不自动选择首项；保存许可源信息与版本，不能把Geo回包混入开放城市库。

下一步选择GeoNames开放许可路线或先确认和风官方列表的本地授权。之前“仅保存用户输入”是被讨论的候选，不视为用户当前已选定存储方案。

## 5. 命令与查询流程建议

以下为拟议语义，尚未实现：

```text
天气 北京        # 无需 @ 的一次天气查询
天气 北京 朝阳   # 具体行政区语法需在实现时明确，避免歧义
天气            # 提示输入城市；若已批准偏好功能则复用用户自有输入
天气城市 北京   # 可选：保存用户自己输入的默认城市文字
天气城市 删除   # 可选：删除默认偏好
```

```text
规范化群命令 → 用户输入／本地自有偏好
  → CityResolver（最终城市源待确认）
       ├─ 获准本地城市库：搜索／行政区消歧
       └─ GeoAPI实时搜索：返回字段不长期落库
  → 明确城市与坐标（本地优先仍为建议）
  → 有效天气缓存？
       是：显示缓存与时效
       否：预算占位 → v1每日预报 → 天气缓存 → 格式化／来源 → 官方QQ回复
```

- 天气预报可合理缓存，建议首版约1小时并按地点本地跨日失效；缓存 key、是否保留与地理数据关联须结合授权范围设计，不通过缓存变相建立 Geo 数据库。
- 缓存需带数据时间／获取时间与地点日期，提供清除机制；额度耗尽时不得把失效缓存伪装最新预报。
- 同城市并发请求可合并已进行的天气获取，避免重复外发；合并不是地理数据永久缓存。
- 错误提示分别处理无结果、同名地区、鉴权、权限、额度、429与临时网络失败；只有合理短暂错误有界重试，每次尝试重新计入预算。
