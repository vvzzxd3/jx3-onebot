# 需求记录规则

本目录面向开发代理，纳入 Git；不是临时缓存，也不是正式文档。现行开发约束见 [AGENTS](<../../AGENTS.md>)，使用与维护说明见 [正式文档](<../../docs/README.md>)。

## 入口与上下文边界

1. 开始任务先读 [活跃需求索引](<INDEX.md>)，按需求 ID、目标、验收范围、标签和关联定位已有需求，再读相关主记录。**新会话、日期变化、上下文恢复都不是新建需求的理由。**
2. 默认仅加载相关活跃需求和现行规范，不遍历历史归档；不得因目录存在就自动加载全部笔记。
3. 归档只用于用户要求的历史查询或必要的来源追溯，**不具有当前决策效力**。不得把归档中的实现、提案、批准或驳回当作当前约束，也不得自动注入为负面提示词。历史关联不代表继承结论。
4. 活跃记录也必须区分当前要求、已确认决策、假设与待验证事实。旧材料迁入 active 不等于重新确认；标为 `needs-review` 的旧正文仅供核对，不自动生效。
5. 长期有效的架构、业务和安全规则必须固化到现行开发规范或正式文档；任务记录不能成为这些规则的唯一来源。新要求与现行规范有冲突时明确核实，不以旧记录覆盖当前要求。

## 建档与拆分

- 纯咨询、状态查询、代码解释、未形成明确需求的讨论默认不建档。明确要求保留的提案、已批准变更、有实质决定的独立问题才建档。
- 一个需求对应 `active/REQ-YYYYMMDD-short-name/`，ID 建档后永久不变。日期为建档日期，不按会话重命名。
- 小需求只建立 `index.md`，使用 [统一模板](<templates/task.md>)；复杂需求才按需拆出 `proposal.md`、`implementation.md`、`decisions.md`，主记录链接它们。不得机械创建空文件。
- 跨模块需求只建一个主需求，以 `modules` 与 `tags` 关联模块，不在每个模块复制记录。
- 同一目标、同一验收范围持续更新同一需求；可独立批准、实施、验收的目标才拆分。归档后追加功能或发现问题，新建关联需求，不能恢复或修改旧包。
- 记录可审阅摘要、依据、变更和证据，不保存逐字内部推理、会话全文、凭据或未经脱敏个人信息。

## 类别不是生命周期

`proposal`（提案）、`implementation`（实施）、`rejection`（驳回）是记录类别，可共存于同一需求。小需求用章节标识，拆分文件可标注 `category`，仍归属相同 `requirement_id`。

- 提案：来源、目标／非目标、方案、风险、验收条件、批准情况。提出方案不等于授权实施。
- 实施：实际改动、关键决定及依据、偏差、验证与未完成事项。影响范围、行为、接口、配置、数据、决策和验收的变化必须同步；不记录逐行编辑流水。在关键决定后、阶段验证后、会话交接前及收尾前更新。
- 驳回：明确对象是整个需求还是备选方案，并记录否决原因、确认来源、适用条件和替代方向。Agent 的建议不冒称维护者否决。在需求活跃期仅按相关性加载已确认且仍适用的驳回摘要；随需求一起归档，不永久保留在默认上下文。

## 生命周期与提交

主记录状态 `status` 使用：

| 状态 | 含义 |
| --- | --- |
| `proposed` | 已提出，未开始；是否批准另看 `approval` |
| `in-progress` | 已获授权并正在实施 |
| `blocked` | 暂停或缺少信息，写明阻塞；不是完成 |
| `needs-review` | 迁入的旧需求状态／验收／提交边界待核实，不自动执行 |
| `ready-to-archive` | 约定范围已处理，等待获授权的收尾提交 |
| `archived` | 整个需求已归档，不再更新 |

`approval` 独立记录 `pending`／`approved`／`rejected`／`unknown`；`outcome` 使用 `completed`／`rejected`／`cancelled`／`superseded`，未结束可留空。

正常流程：提案 → 实施 → 待归档 → 归档。整体驳回、取消、替代即使没有代码交付，也记录结论并经记录收尾提交一起归档。中间 Git 提交不触发归档。

### 收尾清单

1. 按约定验收范围确认交付、验证和文档同步。若真实联调属于验收范围，未完成就不能归档；仅约定离线交付时明确未联调边界。
2. 将长期有效结论固化到现行规范，补全实际结果、限制和后续需求关联；不把遗留必做项悄悄变成已完成。
3. 尚未获授权提交时留在 active，标记 `ready-to-archive`；**文档规则不授予自动暂存、提交或移动其他未完成任务的权限**。
4. 获授权执行收尾提交时，将该需求的提案、实施、驳回、附件整体迁入 `archive/<归档年份>/<REQ-ID>/`，更新主记录为 `archived`，补归档日期及结果，修正链接，更新活跃与历史索引，再与交付一起提交。无需“先提交再归档”的第二次提交。
5. 不在提交内要求填写该提交自身的哈希；由 Git 路径历史追溯收尾提交。如提交失败，明确未完成收尾，不宣称归档已提交；需要调整时先恢复为待归档工作区状态。
6. 归档收尾后内容冻结，纠错写入新的关联需求，不修改原包。安全／隐私清理可例外处理，须明确授权并留非敏感审计说明，不能因冻结阻止清除泄露内容。

## 关联方式

- `id` 标识需求，`tags` 用于检索，`modules` 表示影响模块。
- `relations` 是带类型的关联列表：`depends-on`（依赖）、`follows-up`（后续）、`supersedes`（替代）、`related-to`（相关）、`historical-context`（历史背景）。目标使用稳定 ID。
- 主记录同时提供普通 Markdown 相对链接，保证无需特定笔记软件即可导航；移动时更新所有受影响链接，ID 不变。
- 独立文件在主记录中注册类别、用途和链接；不为每个会话建立文件。确认来源用可理解的需求摘要和必要会话标识，不依赖隐藏会话才能理解。
- 活跃索引只列未归档需求和简短状态，不累积历史决策；[历史索引](<archive/INDEX.md>)仅为显式查询提供入口。

## 旧记录首次迁移

旧记录按需求归组，不按文件逐个新建需求。明确撤销、替代或已结束的旧需求在本次迁移中标记 `ready-to-archive`，在获授权的收尾提交中再整体归档；不能因为正文写过“完成”就推断原任务已经提交或已上线。未完成或状态不明的需求留在 active，分别标注待批准／待核实；历史阶段测试不冒称本次结果。

迁入的旧正文置于需求包 `legacy/`，只做必要的相对链接修正和历史提示，保留原有结论及其时间语境；**旧正文仅供追溯，旧流程和旧决定不因仍在 active 就继续生效**。待归档包仅待收尾，不属于默认实施上下文，不重新执行其中旧待办；日常任务只需读取索引中的状态，按相关性进入真正活跃的主记录。迁移清单记录旧路径、新路径和完整性信息，归档后不再回写。正式部署、架构、使用说明和公开参考资料不因旧路径相邻而一并归档。
